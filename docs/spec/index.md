# Tsubame 仕様書

独自ドメインのメールを Cloudflare 上で送受信する自前のメール基盤。
**人間と AI エージェントが同じ API を使う**ことを前提に設計している。

## 次に何をするか

- **人がやること**（Cloudflare の操作）は [あなたがやること](../user-todo.md) に 2 件。
  Turnstile の有効化とステージングの作成で、**エージェントでは進められない**。
- コードの残作業は [これからやること](todo.md)。**残りの実装は無い。**
  「実機でしか確かめられないこと」が 4 件あり、それ以外は
  [やらないと決めたもの](constraints.md) として残している。

## この文書の読み方

**唯一の真実は要件と設計の 2 つ。** 迷ったらこの 2 つに従う。

- [要件](requirements.md) — 何を実現するか。`FR-1` … の番号が付く。
  **各要件には、それを検証する e2e が必ず 1 つ以上ある**（下の「検証状況」を参照）。
- [設計](architecture.md) — どう作るか。ディレクトリの所有権、データモデル、API 契約。

以下は上の 2 つを補う記録。

## 仕様と検証がずれない仕組み

要件と e2e は機械で突き合わせている。**ドキュメントを腐らせないのはこの 3 つのゲート。**

| 検査 | 落とすもの |
| --- | --- |
| `npm run spec:coverage` | 要件はあるのに e2e が無い |
| `npm run spec:drift` | 実装を変えたのに要件も e2e も触っていない |
| `npm run check:comments` | コードを読めば分かることを書いたコメント |

どれも CI で走る（`spec:coverage` は push と pull request、`spec:drift` と `check:comments` は pull request のとき）。
要件を書き足すと、e2e を書くまで CI が通らない。

## 書くときの決まり

- **リンクは `.md` で書く。** `npm run doc` が `.html` に置き換えるので、GitHub でもビルド後でも読める。
- 役目を終えた文書は残さず消す（経緯は git に残る）。「正はどこか」を必ず 1 行で示してから消す。
- 実環境の値（実ドメイン・実アドレス・アカウント ID）は書かない。`example.com` などに伏せる。
