分類は 3 つ。**「1. 実装する」だけが手を動かす対象**で、2 と 3 は「やらないと決めたこと」の
置き場所（消すと同じ議論をまた一からやる羽目になるので残す）。

| 分類 | 意味 | 今 |

| 1. 実装する | コードを変えれば終わる | **無し** |

## 1. 実装する

**今は無い。** 見つけたら、コードを読んで確かめてから B-n として足す。

直すときは [受け入れた制約](constraints.md) §3「再発しやすい型」を先に読む。

B-33 / B-34 / B-35 は 2026-09-13 に片付けた。
要点だけ残す（B-33 / B-34 は「[受け入れた制約](constraints.md) §3 の型」に当てはまっていた）。

- **B-33** — 会話の未読数（`threads.unread_count`）に入るのは「未読かつゴミ箱でない」メールだけ、と
  定義を 1 つに決めた。既読化の PATCH だけが減算し、ゴミ箱への移動は減算しないという非対称が
  ドリフトの原因だったので、`messages.ts` の PATCH で**両方の遷移を同じ式で数え直す**形にした。
  送信控えを既読で作る側（`outbound.ts`）は `7aed761` で既に直っていた。
- **B-34** — 一覧が `direction` を持っていなかったので、`ThreadRow` に `lastDirection`（最新のメールの向き）を
  足して API の契約に載せ、送信控えの行にだけ「送信」の印を出す（`SentMark.tsx`）。
  検索画面はメッセージ単位なので元から `direction` を持っており、印を足すだけで済んだ。
- **B-35**（2026-09-13）— 表示名を **Tsubamail** にした。Webhook の署名と転送ループ検出の
  ヘッダも `X-Tsubamail-*` に変えた（どちらもまだ使っていないので、受け手を壊さないうちに揃えた）。
  **リポジトリ名（`tsubame-mail`）と Worker 名（`tsubame`）は変えていない**——Worker 名は
  Email Routing のルール宛先と一致していなければ受信が止まる（`requirements.md` §5）。
  ロゴは燕のシルエットで文字が入っていないため、変更不要だった。

## 2. 実機でしか確かめられない

走らせないと分からないもの。**直す作業ではなく、確かめる作業**。
確かめた結果は [受け入れた制約](constraints.md) §2 に移すか、成立したら上の「1. 実装する」に B-n として起こす。

| 何を確かめるか | なぜ確かめられていないか | 出典 |
| --- | --- | --- |
| Cloudflare の `Authentication-Results` が欠けるのはどんなメールか（#127） | Gmail 側に自動転送の設定が要る。公開されている報告は workerd の issue #6740 だけで、Cloudflare からの回答は無い。欠けても未認証扱いになり安全側に倒れる | constraints §2 |
| 本番の Workers Logs に drizzle のクエリ失敗がどう残るか（#146） | `redactError` を通すようにしたが、実機のログの形を見ていない | constraints §2 |
| `X-CF-SpamH-Score` が 5 以上になるメールがあるか（#128 / #140） | 露骨な見本は Email Sending が送信時に拒否するので、外から届くメールで観測できていない。実運用で値が集まったら `parse.ts` `spamVerdictFromScore` を見直す | constraints §2「受信」 |
| push サービスのどの 4xx を恒久的な失敗とみなすか（#131） | 実挙動を見ていない。今は 4xx が 3 回続いた端末を無効にしている | constraints §2「プッシュ通知」 |

`LOGIN_RATE_LIMIT` / `SEND_RATE_LIMIT` の実機の挙動（#106）は 2026-09-13 に確かめた。
**binding が本番で一度も発火しない**ことが分かり、[受け入れた制約](constraints.md) §2「認証・キー」に #147 として移した。

**検証で本番の送信ドメインを使わない。** スパムの見本や存在しない宛先に送ると
送信ドメインの評判（Bounce rate / Spam rejection rate）が落ち、Cloudflare が送信を止めうる
（constraints §2「送信」）。

  修正前に保存された行）と [日々の運用](../ops/operations.md) §6 のチェックリスト。
- **デプロイのときに要る作業** — [受け入れた制約](constraints.md) §1。手順は
  [デプロイ](../ops/deployment.md) §5.3 と [日々の運用](../ops/operations.md) §8。
- **作らないもの** — [要件](requirements.md) §4 の非目標。
