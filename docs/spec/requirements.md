# 要件定義 — tsubame

独自ドメインのメールを Cloudflare 上で送受信し、**人間と AI エージェントの双方が
同じ API で使える**自前のメール基盤。

## 1. 利用者と権限

| ロール | できること |
| --- | --- |
| `owner` | 全権。ドメイン・アドレス・ユーザー・API キー・ルール・Webhook の管理。メールは他の人と同じく自分に割り当てたアドレスだけを見る。全アドレスの閲覧は**管理者モード**のときだけ（FR-19）。 |
| `member` | 自分に割り当てられたアドレスのみ読み書き。自分のプロフィールと自分の API キーのみ変更可。 |
| `agent` | AI 用。UI にはログインせず API キーのみで動く。権限は member と同じ仕組みで、割り当てられたアドレスに限定。 |

- オーナーは 1 人（複数可だが初期は 1 人）。社内メンバーはオーナーが作成する。自己登録は無い。
- 「自分のアカウントのみいじれる」= 他人のアドレス・他人のキー・全体設定には一切触れない。

## 2. 機能要件

### FR-1 受信
- Cloudflare Email Routing で受けたメールを Worker が受け取り、生 MIME を R2 に保存し、
  キュー経由でパースして D1 に保存する。
- 複数ドメイン・複数アドレスを同時に扱う。
- 宛先解決の順序は「拒否 → 実在アドレス（`+タグ` を落として解決・エイリアス展開）→ forward / deliver / drop →
  catch-all フォールバック」。catch-all が実在アドレスを覆い隠してはならない。
- **サブアドレス（`tanaka+github@example.com`）を受け付ける。** 完全一致に外れたら
  `+タグ` を落とした基本アドレスで解決する。catch-all より先に評価する。
  ただし Cloudflare 側は個別ルールでタグ付きを拾えないため、**タグ付きを届かせるには
  そのドメインの catch-all を有効にする必要がある**（既定では無効）。
- 受信は `In-Reply-To` / `References` で既存の会話につなぐ。他人の Message-ID を名乗るだけの第三者のメールは、
  差出人ドメインの認証（DMARC か DKIM）が通らなければ既存の会話に混ぜない。
- 25MB を超えるメールは R2 に置く前に受信ハンドラで拒否する。

### FR-2 送信
- 自分に割り当てられたアドレスから送信できる。差出人詐称は不可（サーバ側で検証）。
- 返信はスレッドを維持する（`In-Reply-To` / `References` を引き継ぐ）。
- 添付ファイルを送れる。
- 送信は `outbound_jobs` で状態を持ち、失敗は再試行する。
- 件名は 600 バイトまで。超えたら 400 で拒否し、黙って切らない。返信で「Re: 」を足して超えるときは元の件名を末尾から切る。

### FR-3 検索（重点機能）
- **API から強力に検索できることを最優先**。AI エージェントが自律的に読み込むための主要導線。
- 日本語の部分一致が効くこと。方式は FTS5 `trigram`（3 文字以上の語に効く。1〜2 文字の語は `LIKE` で補う）。
  詳細は [検索方式の決定](adr-search.md)。
- 絞り込み: アドレス、送信者、宛先、件名、本文、期間、未読、添付有無、方向、スレッド。
- カーソルページング。件数上限は既定 25 件・最大 100 件。

### FR-4 アカウント管理
- オーナーがユーザーを作成し、アドレスごとに `read` / `write` を付与する。パスワードは 12 文字以上。
  最後のオーナーは降格・無効化・削除できない。
- パスワード認証 + セッション Cookie（UI 用）。
- **最初のオーナーは `INTERNAL_SECRET`（20 文字以上）を知っている人しか作れない。**
  オーナーは Cloudflare の DNS とメールルーティングまで触れるため、デプロイ直後に
  URL を見つけただけの相手に取られてはならない。未設定なら誰も作れない。
  オーナーが 1 人でも居れば作成経路は閉じる。
- 利用者は**外部アドレス**（Gmail など、このアプリの外のアドレス）を持てる。全利用者で一意。外部アドレスは、そこへ送った
  確認コードを画面で入れて**確認済み**にする（コードは 30 分で切れ、試行回数に上限がある）。確認メールは、送信が有効な
  ドメインのアドレス（本人のプライマリを優先）から送る。送れるアドレスがまだ無ければ、できた時点で送り直せる。
  ログインは**プライマリアドレス**か**確認済みの外部アドレス**でできる。
- member と agent には必ず**プライマリアドレス**（このアプリで受信する内部アドレス。例: 田中さんに `tanaka@example.com`）を 1 つ割り当てる。
  作成時に、既存のアドレスを選ぶかその場で作る。プライマリは `write` で割り当てられ、後から変えられる
  （その人に `write` で割り当てたアドレスの中から）。外部アドレスは作成の後から本人かオーナーが登録する。
  プライマリと外部アドレスは、どの利用者のプライマリ・外部アドレスとも重ならない。
- 最初のオーナーは、作成時に外部アドレスを必ず設定し、確認前でもそれでログインできる（プライマリがまだ無いため）。
  ドメインを繋いでから最初に作ったアドレスがそのオーナーのプライマリになる。送信できるアドレスができたら、画面から外部アドレスの確認メールを送る。

### FR-5 API キー
- **キー単位**でスコープ（`read` / `send` / `admin`）と**対象アドレス**を限定できる。
  キーがユーザー単位でしかスコープできないと、AI 用キーから他人の受信箱が読めてしまう。
  これを構造的に潰すことが本要件の中心のひとつ。
- 発行時のみ平文を表示し、保存はハッシュのみ。失効・有効期限・最終使用時刻を持つ。
- 平文は保存しないので同じトークンは復活できない。なくしたら失効させ、同じ設定で**再発行**する
  （差し替えは旧キーを失効させて同じ設定で作り直す）。
- **絞られたキーからより広いキーは作れない**。対象アドレス・期限を制限した admin キーは管理の変更ができず（403）、
  自分より広いスコープ・対象アドレスのキーを作ると 403 になる。期限は自分の期限に、対象アドレスを省けば自分の範囲に黙って狭める。
  対象アドレスを絞った admin キーでは、管理 API から他のキーを失効させることもできない。
- **キーで発行したキーは、発行に使ったキー（親）に連なる**。親の失効・差し替え、持ち主の削除・パスワード変更・無効化で、
  そこから（孫以降も含めて）発行したキーも失効する。漏れたキーから作られたキーが生き残らないようにするため。

### FR-6 ドメイン管理
- Cloudflare の zone 一覧から選んで接続する。多数のドメインを同時に管理する前提。
- **apex を保護する**: 既存 MX（例: Google Workspace）を検知し、apex を奪う操作は明示的な
  確認なしに実行しない。既定はサブドメイン運用（`mail.example.com`）。
- catch-all は**ドメインごとの明示的なオプトイン**。既定で有効にしない（ゾーン単位で全メールを飲むため）。
- 接続時に Email Routing / Email Sending の DNS を整える。切断時は後始末する。
  接続後の状態は**再検査（verify）**で確認できる。
- Email Sending はドメインごとに有効・無効を切り替えられる（接続した後からでもよい）。**無効にしたドメインからは送らない**
  （送信 API は 409、無効にする前に積まれた送信は `failed`）。無効化は DNS と Cloudflare 側の設定を消さない。

### FR-7 ルーティングルール
- ドメインスコープ: 受信時に `deliver` / `forward` / `reject` / `drop` を決める。
- アドレススコープ: 配信後の振り分け（既読、スター、破棄など最小限）。

### FR-8 Webhook
- 新着受信・送信完了などのイベントを外部 URL に POST する。イベントは
  `message.received` / `message.sent` / `message.failed` の 3 種。
- 署名はヘッダ `X-Tsubame-Signature` に `t=<unix秒>,v1=<HMAC-SHA256>`（`t.body` を HMAC）で付ける。
- URL は https の公開ホストのみ。内部・予約済み IP や `localhost` 系の宛先は不可。
- 失敗は 30 秒 / 300 秒 / 1800 秒の指数バックオフで**最大 5 回**まで再試行する。
  配信履歴（`deliveries`）を見られ、失敗ジョブは手動で再送できる。再試行の予定（無ければ作成）から 30 分以上
  `pending` のまま止まった配信も手動で再送できる。同じ試行が重なっても受け手に届くのは 1 回。
- 受け手への POST はキューで行い、受信・送信の処理を待たせない。
- Webhook は owner の管理の設定なので、見るメールの範囲（FR-19）には縛られない。owner は自分に割り当てていない
  アドレスも対象にでき、その新着も届く。作成・変更・削除は監査ログに残る。

### FR-9 UI
- 日本語ネイティブ。翻訳レイヤーは持たない。
- **作り込まない**。受信箱一覧 / 本文 / 返信・新規作成 / 検索 / 管理画面 のみ。
- 設定項目は最小限（表示名、署名、パスワード変更程度）。
- **署名はメールボックスごと**に持つ。そのメールボックスに `write` の割り当てがある利用者（owner は全部）が、
  画面のログインから変えられる。API キーでは変えられない（人が書くメールに差し込まれるため）。変更は監査ログに残る。
- 受信 HTML の本文にあるリンクは、本文の枠の中ではなく新しいタブで開く。開けるのは `http(s)` と `mailto` だけ。

### FR-10 添付と生 MIME
- 添付と生 MIME は R2 に置く。取得は恒久 URL（`/v1/attachments/{id}`・`/v1/messages/{id}/raw`）で、
  **毎回認可**を通過したときだけ取得できる。事前発行の一時 URL は張らない。
- ゴミ箱のメッセージの添付と生 MIME は、本体と同じく `?includeTrash=true` を付けたときだけ取得できる。

### FR-11 共有メールボックス

- 1 つのアドレスを**複数のユーザーに割り当てられる**（問い合わせ窓口のような共有受信箱）。
- 割り当ては `read`（読むだけ）と `write`（送信もできる）の 2 段階。
- オーナーは、あるアドレスを誰が見られるかを一覧できる。
- 共有していても、割り当てられていないユーザーには**一切見えない**。
- **オーナーも含めて、自分に割り当てたアドレスのメールしか見えない**。他の人に割り当てたアドレスは、
  自分にも明示的に割り当てない限り見えない（アドレスと人は多対多）。

### FR-12 メンバー自身の API キー

- オーナーでなくても、**自分の API キーを自分で発行・失効できる**。
- 発行したキーは**本人の権限を超えない**。本人が触れないアドレスはキーでも触れない。
- キーの対象アドレスとスコープは、本人の権限の範囲内でさらに絞れる。
- 他人のキーは一覧も失効もできない。
- 自分のキーも発行・失効に加えて、失効したキーと同じ設定で**再発行**できる。

### FR-13 仮パスワードと初回変更

- オーナーがメンバーを作るとき、パスワードを指定しなければ**仮パスワードを発行**する。
- 仮パスワードは**作成の応答で 1 度だけ返る**。保存するのはハッシュのみ。
- 仮パスワードで入った本人は、**変更するまで他の画面に進めない**。
- パスワードを変えると、その利用者の全セッションを落とし、発行済みの API キーも**全失効**させる。

### FR-14 メールボックスの色

- 一覧で見分けるための色をメールボックスごとに持つ。
- 既定は 20 色から**未使用の色を優先して**割り当て、全部使われていれば作成順に譲る。任意の色（`#rrggbb`）も指定できる。
- 横断表示のときは、どのメールボックス宛かが色と文字で分かる。

### FR-15 ホーム画面に追加（PWA）

- Web App Manifest と Service Worker を配り、iOS / Android / PC のブラウザで
  「ホーム画面に追加」「インストール」ができる。起動はアドレスバーのない単独ウィンドウ。
- スマホ幅（768px 未満）では、スマホ用の配置に切り替わる（[スマホ画面設計](mobile-screens.md)）。
- オフライン時もアプリの殻は開き、「オフラインです」を出す。**メール本文はオフライン保存しない**
  （端末紛失時に残るものを増やさない）。Service Worker は `/api/*` をキャッシュしない。
- 追加の案内は、追加していない・スマホで開いている・3 回目以降の訪問、のときだけ出す。
  閉じたら 30 日出さない。
- 他のアプリの「共有」から tsubame を選ぶと、作成画面に件名と本文が入った状態で開く（manifest の `share_target`）。

### FR-16 プッシュ通知

- 端末ごとに通知を購読できる。1 人が複数の端末を持てる。購読と設定の API は**セッション限定**
  （API キーでは 403）で、自分の分しか触れない。ロール `agent` は対象外。
- 通知の対象イベントは **新着受信** と **送信失敗**。送信失敗は**そのメールを送った本人にだけ**通知する。
- 通知の判定は [PWA とプッシュ通知](pwa-notifications.md) の「4. 通知の判定」の順で行い、
  **判定の理由を利用者が後から確かめられる**（通知欄）。
- 一時停止中・おやすみ中に止めた分は通知として出し直さず、通知欄に束で残す。
- 権限の変化は即座に効く。アドレスの割り当てを外されたら、そのアドレスの通知は次の 1 通から来ない。
- **パスワードを変えると、その利用者の全端末の購読を消す**。その端末でログアウトすると、その端末の購読を消す。
  90 日開かれていない端末の購読は自動で消す。
- 既定値だけで正しく動く: 割り当てられたメールボックスの新着を、差出人と件名つきで通知。
  キャッチオールの受け皿も、割り当てられた人にだけ通知する（owner でも割り当てが要る）。スパム判定は通知しない。
- 通知の設定は FR-9「設定は最小限」の**例外**とする。代わりにトップはプリセットで済ませ、細かい設定は奥に畳む。
- Web Push の送信（VAPID と本文の暗号化）は依存を足さず WebCrypto で自前実装する。
- アプリのバッジ（未読の数）は、画面を開くたびにサーバの数で付け直す。
- push サービスが購読の消滅（404 / 410）を返した端末は消す。

### FR-17 PC の読み進め

- 会話を開いたまま、一覧の順で**次へ / 前へ**移れる。一覧の絞り込み・位置は会話を閉じても保つ
  （通知から開いた会話を閉じたときも同じ）。
- 768px 以上では、一覧と本文を左右に並べる**分割ビュー**を既定にする。本文だけを広げる**全画面**の導線を持つ。
  どちらを既定にするかは端末ごとに選べる（表示の設定なので localStorage に置き、サーバの設定は増やさない）。
- 一覧で複数の会話を選び、**まとめて既読・未読・ゴミ箱へ**できる（PC のみ。スマホは出さない）。
- FR-9「作り込まない」の例外として、この 3 点に限って認める。

### FR-18 管理画面の詳細と監査ログ

- 管理の一覧（ドメイン・アドレス・ユーザー・API キー・ルール・Webhook）は省略して並べ、各行から**詳細**を開ける。
  詳細は API が返せる情報を省略せずに出す（対象アドレスの全件、権限、配下のアドレス、配信履歴の全件など）。
- **監査ログ**を API（`GET /v1/admin/audit-logs`）で読める。対象（種類と id）・実行者・操作で絞り、新しい順にカーソルで辿る。
  詳細の画面は、その対象に関わる操作の記録を出す。owner のセッションか、アドレスを絞っていない admin キーだけが読める。
- 共有メールボックスの設定の変更（署名など）や、キー・ユーザー・ドメイン・アドレス・ルール・Webhook の変更は監査ログに残す。
  秘密（トークン・パスワード・Webhook の secret・署名の本文）は残さない。
- 失効・削除・切断のような取り消せない操作は、見て分かるボタンにし、確認を挟む。

### FR-19 見るメールの範囲（管理者モードと非表示）

- **管理者モード**: owner だけが画面から入れ、入っている間は全アドレスのメールを**読める**（送信・既読・ゴミ箱などの変更は、自分に割り当てたアドレスだけ）。
  モードはそのログインのセッションにだけ持ち、1 時間で自動的に切れる。API キーでは入れない。入った・出たは監査ログに残す。
  モード中は画面に常にそれと分かる帯を出す。
- **非表示**: 自分に割り当てられたメールボックスごとに「非表示」にできる。非表示のメールボックスのメールは、
  まとめた受信箱・一覧・検索の既定から外れ、上部の絞り込みでそのメールボックスを選ぶか「非表示も表示」にしたときだけ出る。
  非表示は見え方の設定で、権限と通知は変えない（通知は通知設定に従う）。

## 3. 非機能要件

- Cloudflare Workers / D1 / R2 / Queues のみで完結する。外部 SaaS 依存を増やさない。
- Workers は常駐しないため **IMAP / POP3 は提供しない**。代替は API と Webhook と転送。
- 型は本番ビルドで検査する（`tsc --noEmit` を CI で必須にする）。
- テストを最初から持つ（`vitest` + `@cloudflare/vitest-pool-workers`）。
- シークレットは Worker Secret に置く。リポジトリにアカウント固有 ID を書かない。

## 4. 非目標（作らないもの）

カレンダー、連絡先管理（CRM 的なもの）、mbox インポート/エクスポート、バックアップ UI、
課金・ライセンスゲート、ブランディング差し替え、アプリ自己アップデート、
スパム学習基盤（ベイズ・レピュテーション）、WebSocket リアルタイム、キーボードショートカット、
テンプレート、スヌーズ、ユーザー作成フォルダ。

スパムは「Cloudflare が付けた判定ヘッダを読むだけ」に留める。

## 5. Cloudflare でメールを扱うときの落とし穴

1. **catch-all はゾーン単位**。apex の MX を Cloudflare に向けた瞬間、全社メールが吸い込まれる。
2. **CF_TOKEN の zone スコープ**はドメインを増やすたびに広げ直す必要がある。UI に明示する。
3. **Worker 名 = Email Routing ルールの宛先 = service binding 名**。3 箇所を一致させる。
   リネームすると受信が止まる。
4. `message.setReject()` / `message.forward()` は **email ハンドラでしか呼べない**。
   キューのコンシューマからは呼べないので、拒否・転送の判定は受信ハンドラ内で完結させる。
5. **`to` / `cc` はリストになりうる**。単一アドレスとして扱う実装は必ず壊れる。
6. **メール本文をハンドラ内でパースしない**。R2 に置いてキューに逃がす。
7. スキーマの二重管理（マイグレーションとブートストラップ SQL の重複）を作らない。
