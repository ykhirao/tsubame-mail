# 要件定義 — tsubame

独自ドメインのメールを Cloudflare 上で送受信し、**人間と AI エージェントの双方が
同じ API で使える**自前のメール基盤。

## 1. 利用者と権限

| ロール | できること |
| --- | --- |
| `owner` | 全権。ドメイン・アドレス・ユーザー・API キー・ルール・Webhook の管理。全アドレスの閲覧。 |
| `member` | 自分に割り当てられたアドレスのみ読み書き。自分のプロフィールと自分の API キーのみ変更可。 |
| `agent` | AI 用。UI にはログインせず API キーのみで動く。権限は member と同じ仕組みで、割り当てられたアドレスに限定。 |

- オーナーは 1 人（複数可だが初期は 1 人）。社内メンバーはオーナーが作成する。自己登録は無い。
- 「自分のアカウントのみいじれる」= 他人のアドレス・他人のキー・全体設定には一切触れない。

## 2. 機能要件

### FR-1 受信
- Cloudflare Email Routing で受けたメールを Worker が受け取り、生 MIME を R2 に保存し、
  キュー経由でパースして D1 に保存する。
- 複数ドメイン・複数アドレスを同時に扱う。
- 宛先解決の順序は「拒否ルール → 実在アドレス → エイリアス → catch-all フォールバック」。
  catch-all が実在アドレスを覆い隠してはならない。
- **サブアドレス（`tanaka+github@example.com`）を受け付ける。** 完全一致に外れたら
  `+タグ` を落とした基本アドレスで解決する。catch-all より先に評価する。
  ただし Cloudflare 側は個別ルールでタグ付きを拾えないため、**タグ付きを届かせるには
  そのドメインの catch-all を有効にする必要がある**（既定では無効）。

### FR-2 送信
- 自分に割り当てられたアドレスから送信できる。差出人詐称は不可（サーバ側で検証）。
- 返信はスレッドを維持する（`In-Reply-To` / `References` を引き継ぐ）。
- 添付ファイルを送れる。
- 送信は `outbound_jobs` で状態を持ち、失敗は再試行する。

### FR-3 検索（重点機能）
- **API から強力に検索できることを最優先**。AI エージェントが自律的に読み込むための主要導線。
- 日本語の部分一致が効くこと（形態素解析なしで成立する方式を採る）。
- 絞り込み: アドレス、送信者、宛先、件名、本文、期間、未読、添付有無、方向、スレッド。
- カーソルページング。件数上限あり。

### FR-4 アカウント管理
- オーナーがユーザーを作成し、アドレスごとに `read` / `write` を付与する。
- パスワード認証 + セッション Cookie（UI 用）。
- **最初のオーナーは `INTERNAL_SECRET`（20 文字以上）を知っている人しか作れない。**
  オーナーは Cloudflare の DNS とメールルーティングまで触れるため、デプロイ直後に
  URL を見つけただけの相手に取られてはならない。未設定なら誰も作れない。
  オーナーが 1 人でも居れば作成経路は閉じる。
- ログイン用のメールアドレスは、このアプリで受信するアドレスでなくてよい（Gmail など）。

### FR-5 API キー
- **キー単位**でスコープ（`read` / `send` / `admin`）と**対象アドレス**を限定できる。
  キーがユーザー単位でしかスコープできないと、AI 用キーから他人の受信箱が読めてしまう。
  これを構造的に潰すことが本要件の中心のひとつ。
- 発行時のみ平文を表示し、保存はハッシュのみ。失効・有効期限・最終使用時刻を持つ。

### FR-6 ドメイン管理
- Cloudflare の zone 一覧から選んで接続する。多数のドメインを同時に管理する前提。
- **apex を保護する**: 既存 MX（例: Google Workspace）を検知し、apex を奪う操作は明示的な
  確認なしに実行しない。既定はサブドメイン運用（`mail.example.com`）。
- 接続時に Email Routing / Email Sending の DNS を整える。切断時は後始末する。

### FR-7 ルーティングルール
- ドメインスコープ: 受信時に `deliver` / `forward` / `reject` / `drop` を決める。
- アドレススコープ: 配信後の振り分け（既読、スター、破棄など最小限）。

### FR-8 Webhook
- 新着受信・送信完了などのイベントを外部 URL に POST する。署名付き。失敗は指数バックオフで再試行。

### FR-9 UI
- 日本語ネイティブ。翻訳レイヤーは持たない。
- **作り込まない**。受信箱一覧 / 本文 / 返信・新規作成 / 検索 / 管理画面 のみ。
- 設定項目は最小限（表示名、署名、パスワード変更程度）。

### FR-10 添付と生 MIME
- 添付と生 MIME は R2 に置き、認可付きの一時 URL 経由でのみ取得できる。

### FR-11 共有メールボックス

- 1 つのアドレスを**複数のユーザーに割り当てられる**（問い合わせ窓口のような共有受信箱）。
- 割り当ては `read`（読むだけ）と `write`（送信もできる）の 2 段階。
- オーナーは、あるアドレスを誰が見られるかを一覧できる。
- 共有していても、割り当てられていないユーザーには**一切見えない**。

### FR-12 メンバー自身の API キー

- オーナーでなくても、**自分の API キーを自分で発行・失効できる**。
- 発行したキーは**本人の権限を超えない**。本人が触れないアドレスはキーでも触れない。
- キーの対象アドレスとスコープは、本人の権限の範囲内でさらに絞れる。
- 他人のキーは一覧も失効もできない。

### FR-13 仮パスワードと初回変更

- オーナーがメンバーを作るとき、パスワードを指定しなければ**仮パスワードを発行**する。
- 仮パスワードは**作成の応答で 1 度だけ返る**。保存するのはハッシュのみ。
- 仮パスワードで入った本人は、**変更するまで他の画面に進めない**。
- パスワードを変えると、その利用者の全セッションを落とす。

### FR-14 メールボックスの色

- 一覧で見分けるための色をメールボックスごとに持つ。
- 既定は 20 色を**作成順に割り当てる**。任意の色（`#rrggbb`）も指定できる。
- 横断表示のときは、どのメールボックス宛かが色と文字で分かる。

## 3. 非機能要件

- Cloudflare Workers / D1 / R2 / Queues のみで完結する。外部 SaaS 依存を増やさない。
- Workers は常駐しないため **IMAP / POP3 は提供しない**。代替は API と Webhook と転送。
- 型は本番ビルドで検査する（`tsc --noEmit` を CI で必須にする）。
- テストを最初から持つ（`vitest` + `@cloudflare/vitest-pool-workers`）。
- シークレットは Worker Secret に置く。リポジトリにアカウント固有 ID を書かない。

## 4. 非目標（作らないもの）

カレンダー、連絡先管理（CRM 的なもの）、mbox インポート/エクスポート、バックアップ UI、
課金・ライセンスゲート、ブランディング差し替え、アプリ自己アップデート、
スパム学習基盤（ベイズ・レピュテーション）、WebSocket リアルタイム、キーボードショートカット、
テンプレート、スヌーズ、ユーザー作成フォルダ。

スパムは「Cloudflare が付けた判定ヘッダを読むだけ」に留める。

## 5. Cloudflare でメールを扱うときの落とし穴

1. **catch-all はゾーン単位**。apex の MX を Cloudflare に向けた瞬間、全社メールが吸い込まれる。
2. **CF_TOKEN の zone スコープ**はドメインを増やすたびに広げ直す必要がある。UI に明示する。
3. **Worker 名 = Email Routing ルールの宛先 = service binding 名**。3 箇所を一致させる。
   リネームすると受信が止まる。
4. `message.setReject()` / `message.forward()` は **email ハンドラでしか呼べない**。
   キューのコンシューマからは呼べないので、拒否・転送の判定は受信ハンドラ内で完結させる。
5. **`to` / `cc` はリストになりうる**。単一アドレスとして扱う実装は必ず壊れる。
6. **メール本文をハンドラ内でパースしない**。R2 に置いてキューに逃がす。
7. スキーマの二重管理（マイグレーションとブートストラップ SQL の重複）を作らない。
