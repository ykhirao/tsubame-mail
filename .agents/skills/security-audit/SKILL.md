`docs/spec/security-audit.md` は「精査（指摘の一覧）→ 対応 → 再検査 → 次の精査」を繰り返す記録。
「進めて」と言われたら、**今どの段階で止まっているかを文書から読み取り、次の 1 段だけ**をやる。
何段進めるかを聞かれなければ 1 段で止め、次に何をするかを報告して終わる。

観点は `docs/spec/security.md`（S-1〜S-11）。指摘の番号は文書全体で通し番号。

## 0. 段階の見分け方

最新の「第 N 回全精査」の節を見る。

| 状態 | 次にやること |
| --- | --- |
| 「まとめ（第 N 回）」はあるが「対応状況（第 N 回）」が無い | **対応**（§2） |
| 「対応状況（第 N 回）」はあるが「再検査（第 N 回）」が無い | **再検査**（§3） |
| 「再検査（第 N 回）」まである | **第 N+1 回の精査**（§4） |
| 再検査で「失敗」があり、その対応が書かれていない | 失敗分だけを §2 の手順で直してから再検査を追記 |

## 1. 役割分担（どの段階でも同じ）

- **本体**（このセッション）: 段階の判断、分担表の作成、統合、文書の追記、コミット。
- **worker**: `model: "sonnet"` の `general-purpose` エージェント。`isolation: "worktree"` で 1 群 1 人。実装とテストとコミットまで。
- **審査役**: `model: "fable"` の `general-purpose` エージェント。worker の差分を読んで受け入れ／差し戻しを判断する。
  `fable` が使えない環境（起動がエラーになる）なら本体が審査する。

worker と審査役は必ず別のエージェントにする。書いた本人に審査させない。
本体が Opus でも、審査は fable に委ねてよい。判断の最終責任は本体にあるので、審査役の報告は読んで納得してから従う。

## 2. 対応

### 2-1. 分担表を書く

文書の「まとめ（第 N 回）」の下に「### 対応の分担（第 N 回）」を足してからコミットする（worker は自分の worktree で文書を読むので、先にコミットが要る）。

- **編集するファイルが重ならない**ように 4〜5 群に分ける。ファイル単位で切る。同じファイルを 2 群が触るなら片方に寄せる。
- 各群の行: 群名 / 指摘番号 / 編集してよいファイル / 前提・注意（群をまたぐ依存、スキーマ変更の可否）。
- `src/db/schema.ts`・`src/api/app.ts`・`wrangler.jsonc` など共有ファイルは、必要な群にだけ「この目的に限り可」と明記する。
- 分担表の末尾に共通ルール（攻撃の再現テスト、`npm run verify`、直せなかったものは番号と理由を報告、報告は 30 行以内）。
- **「変更した API を呼んでいる UI・スクリプト・テストヘルパも同じ群で直す」と必ず書く。** 第 2 回はこれが抜けて、一覧に `limit` を付けた群が管理画面を 25 件で切り、Content-Type を要求した群がローカル seed を壊した。

### 2-2. worker を起動する

1 メッセージで全群を同時に起動する。プロンプトの骨子:

```
担当は群 X「…」。まず AGENTS.md、.agents/skills/comments/SKILL.md、
docs/spec/security-audit.md の「対応の分担（第 N 回）」の群 X の行と担当指摘の本文を読む。
担当: #a, #b, …
編集してよいファイル: …（分担表のとおり）。それ以外は編集せず「要依頼」として報告。
docs/spec/security-audit.md は編集しない（統合担当が書く）。
指摘ごとに元の攻撃を再現するテストを先に書き、直した後に通ることで「直った」を示す。
文書の「直し方」は提案。より良い直し方があれば理由を添えて採ってよい。
変更した API を呼んでいる UI・スクリプト・テストヘルパも自分で直す。
依存は 2026 年秋時点の最新。API は node_modules の型定義で確認する。インデントはタブ。コメントは why だけ。
終わる前に npm run verify を通し、git add -A && git commit -m "<日本語>"。AI の署名は入れない（フックに弾かれる）。
報告（30 行以内）: 指摘ごとに「直した（要点）」か「直さなかった（理由）」、触ったファイル、要依頼、verify の結果、worktree のパス・ブランチ・コミット SHA。
```

### 2-3. 審査する

群の報告が届くたびに、審査役を起動して差分を読ませる。プロンプトの骨子:

```
ブランチ <branch> の <base>..<head> の差分を審査する。担当指摘は #a, #b, …（docs/spec/security-audit.md の本文を読む）。
見るのは順に:
1. 指摘の攻撃が本当に塞がっているか。テストがその攻撃を再現しているか。
2. 変更の外への波及。呼び出し側の UI（src/ui）、scripts/、e2e/harness.ts、tests/helpers.ts、
   キューの再配達やレート制限など実行環境の挙動まで含めて「この変更で他に何が壊れるか」を考える。
3. 担当外ファイルへの変更が無いか。共有ファイルを触っていれば理由が妥当か。
4. 規約（ApiError、Principal.addressIds、parseAddressList、コメントは why だけ、日本語 UI）。
結論は「受け入れ」か「差し戻し（直す箇所を具体的に）」。差し戻しは worker がそのまま作業できる粒度で書く。
受け入れでも、統合時に本体が直すべき小さな抜けがあれば別枠で列挙する。
```

差し戻しは `SendMessage` で同じ worker に送る（worktree と文脈が残っている）。同じブランチに追加コミットさせ、再提出を再度審査する。

審査で第 2 回に実際に見つかった型（次回も同じ所を見る）:
- キューの再配達が即時に来る前提が抜けていて、期限付きの回収が永久に動かない。
- サーバ側に上限を付けたのに、呼び出す UI が 1 ページしか読まない。
- 検査を自分の担当ルータにしか入れておらず、同じ経路の他ルータが素通り。
- 既知の値を拒否するようにしたら、その値に依存するローカル手順が止まる。

### 2-4. 統合する

- 受け入れた群から `git merge --no-ff <branch> -m "群 X: …（#a #b …）"`。
- 全群を取り込んだら `npm run verify`。審査で「本体が直す」とされた抜けを直してコミット。
- 文書に「### 対応状況（第 N 回）— <日付>」を足す。表の列は `# / 対応 / 残る制約`。差し戻した件数と理由、統合時に本体が直したもの、verify の件数も書く。
- 未実装で残したもの（スキーマ変更が要るものなど）は「残る制約」に**太字**で書き、報告でも別枠で挙げる。
- `git worktree remove --force` と `git branch -d` で worker の worktree とブランチを消す（`-d` はマージ済みしか消えないので安全）。

## 3. 再検査

「対応」欄を信用せず、指摘ごとに修正がコードに存在し元の攻撃が今も成立しないかを確かめる。
審査役（fable）に全件を渡してもよいし、群ごとに分けてもよい。可能なものは一時テストや `node` で再現を試みる。

- 「### 再検査（第 N 回）— <日付>」を足す。表の列は `# / 判定 / 根拠`。判定は「修正確認（実証済み）」「修正確認（コードとテスト）」「再検査失敗（実証済み）」のいずれか。
- 失敗があれば、その番号と成立する攻撃を本文に書く。次の「進めて」で直す。
- 修正は効いているが隣に同じ欠陥が残っているものは、次回精査の番号として先に振っておく。

## 4. 次の精査

観点 S-1〜S-11 を 3〜4 群に分けて、各群を審査役と同じモデルのエージェントに読ませる（精査は読み手の強さがそのまま結果に出るので sonnet にはやらせない）。

- 前回までに指摘済みのものは再掲しない。番号は通しで続ける。
- 「実証済み」は実際にコードを走らせて成立を確認したものだけに付ける。推測は載せない。
- 「## 第 N+1 回全精査 — <日付>」の下に「まとめ（第 N+1 回）」の表（`# / 深刻度 / 内容 / 場所`）、「直す順番」、指摘ごとの本文（場所・再現・直し方）、「問題なしと確認した範囲」、「未確認」を書く。形は第 2 回の節に揃える。

## 5. 共通の約束

- コミットメッセージは日本語。AI の署名（Co-Authored-By など）は入れない。フックに弾かれる。
- `docs/spec/security-audit.md` を書くのは本体だけ。worker には書かせない。
- 最後の報告には、取り込んだ群、差し戻した理由、本体が直したもの、残る制約、デプロイ時に要る作業（キュー作成・マイグレーション・シークレット）を書く。
