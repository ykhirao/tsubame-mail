**コメントは負債である。** コードと違って実行されないので、誰も嘘に気づかない。
リファクタするたびに古びていき、放っておくと「コードには A と書いてあるがコメントには B と
書いてある」という状態になる。そのとき読み手は両方を疑わなければならず、コメントが無い場合
より遅くなる。だから**書かないのが既定**で、書くのは負債を負ってでも残す価値があるときだけ。

AI に書かせると、この既定が崩れる。次の行を日本語にしただけの行が無限に増える。
それは何も伝えず、コードを変えた瞬間に嘘になる。

## 判断の順番

1. **消せないか。** コードを読めば分かるなら消す。迷ったら消す。
2. **コードで表せないか。** 変数名・関数名・型・早期 return に落とせるなら、そちらに書く。
   コメントで補う必要がある名前は、名前の方が間違っている。
3. **コミットメッセージや `docs/` に書けないか。** 経緯・設計判断・要件はそちら。
   コードの隣に置く必要があるのは「この行を触る人が、その場で知らないと壊すこと」だけ。
4. ここまで残ったものだけをコメントにする。

## 書いてよい（why）

読んでも分からないこと——なぜそうしたのか、なぜ素直な書き方を採らなかったのか、
何を踏んで直したのか——だけ。

```ts
// ForwardableEmailMessage.raw は長さの分からないストリームなので、
// そのまま R2 に渡すと "must have a known length" で落ちる。
const fixed = new FixedLengthStream(rawSize);

// catch-all より先に見るので、タグ付きが catch-all に落ちることはない。
const candidates = [to, baseAddressOf(to)];

// Hono の compose はハンドラの throw をその場で onError に回すため、
// ミドルウェア形の try/catch では ApiError を握れない。
app.onError(...);

// 総当たりで 1 文字ずつ確かめられないよう、長さでも内容でも早期 return しない。
export function secretEquals(a: string, b: string): boolean {
```

呼ぶ側が**知らないと間違える**契約は JSDoc で外向きに書く。型で表せているなら書かない。

```ts
/** null なら「所有ユーザーの権限そのまま」。値があるとその積集合になる。 */
addressIds: string[] | null;
```

## 書いてはいけない（what）

```ts
// ユーザーを取得する
const user = await getUser(id);

// ループしてメッセージを処理する
for (const m of messages) { ... }

// エラーをキャッチする
} catch (e) {

// 色を設定
setColor(hex);
```

### 名前を言い換えただけの JSDoc

これが一番たまりやすい。`/** ランダムなバイト列。 */ function randomBytes()` は
一文字も情報を足していない。**識別子と型を読んで分かることを書いた JSDoc は消す。**

```ts
/** バイト列を base64url にする。 */          // ← 消す。名前に書いてある
export function toBase64Url(b: Uint8Array): string

/** セッション Cookie の名前。 */              // ← 消す。名前に書いてある
export const SESSION_COOKIE = "rid_session";

/** 壊れた入力では空配列を返す。 */            // ← 残す。呼ぶ側が知らないと間違える
export function fromBase64Url(s: string): Uint8Array
```

### 区切り線・章立て

```ts
/* ------------------------------------------------ ユーザー単位の権限解決 */
// --- ここから送信処理 ---
```

**原則すべて消す。** 章立てが要るほど長いファイルは、コメントではなくファイル分割で直す。

### ファイル冒頭の大きな解説

設計や方針は `docs/spec/architecture.md` と `docs/spec/requirements.md` が唯一の真実で、
ファイル冒頭に写すと二重管理になり、必ず片方が古びる。
冒頭に置いてよいのは、**そのファイルを触る人がその場で知らないと壊すこと**を数行だけ。

```ts
/**
 * D1 スキーマ。変更したら必ず `npm run db:generate` を実行すること。
 */
```

### コメントアウトされたコード

消す。git が覚えている。

## 検査

```bash
npm run check:comments            # 追加されたコメントを検査（正規表現だけ。モデルは呼ばない）
npm run check:comments -- --all   # 差分ではなく全ファイルを見る。密度も出す
npm run check:comments -- --llm   # 灰色のものだけ安いモデルに判定させる（手動のときだけ）
```

CI と `git commit` のフック（`.githooks/pre-commit`）で走るのは**規則だけの判定**で、
モデルは呼ばない。`--llm` は自分で確かめたいときに手で叩く。

フックを有効にする: `npm run hooks:install`

どうしても必要な what コメント（生成コードの注記など）は、その行に `// why:` を付けて
理由を書く。検査ごと外すときは環境変数を使う（pre-commit の時点ではコミットメッセージが
まだ無いので、メッセージ中のタグでは外せない）。

```bash
NO_COMMENT_CHECK=1 git commit -m "..."
```

外すのは例外であって、常用するなら書かない方を選ぶこと。

### 規則で取れないもの

判定は正規表現なので、**複数行に散らした what は取り逃す**。

```ts
// メッセージを一覧して、
// 添付があれば R2 から読み出す。
```

これは「規則では判定できなかった」として件数だけ報告され、コミットは止まらない。
`--llm` を付ければ判定できるが、モデルを呼ぶのでフックと CI では走らせていない。
**機械は最後の網であって、書かない判断は書く側でする。**
